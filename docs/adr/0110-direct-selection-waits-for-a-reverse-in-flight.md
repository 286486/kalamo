# Direct Selection waits for a Reverse Path Direction press in flight

ADR-0109 renumbered the Direct Selection's Anchors and segments at a Reverse Path Direction press, to where the reverse would put them, and #272 numbered them back on a rejection. Until the answer came, the browser still hit-tested and edited its committed Document, which was not yet reversed. So a key the person clicked in that window was numbered against the old Document, and #272 flipped it with the others on a rejection. A drag, a Delete or a convert in the window worked out its `path_edit` from keys and a Document that disagreed. Its indices were then applied after the reverse if the press was accepted, and without it if the press was rejected. Either way, some outcome edited a point the person did not choose (#274).

## Sources

- Adobe, *Select anchor points to modify paths in Illustrator* (helpx.adobe.com/illustrator/desktop/draw-shapes-and-paths/modify-paths/select-anchor-points-in-paths.html): the Direct Selection tool selects the anchor points and segments under the pointer, and the next edit acts on those.
- Illustrator runs a command to its end before it takes the next input. A click or a drag after a press of Reverse Path Direction in the Attributes panel meets the reversed path, so nothing in Illustrator sees the press half done. Kalamo's window between the press and its answer has no counterpart there.
- ADR-0010: browser commands carry no `rev`, and the Document DO applies one socket's commands in order. Ops such as `move_anchor`, `set_handles`, `set_point_type` and `remove_anchor` name an Anchor by its index, and Delete's `set_d` writes each subpath's direction. Neither kind gives the same result before and after a reverse.

## Decision

**The keys stay numbered as the committed Document runs until the press is answered.** The press sends `path_reverse` and draws its preview, but it changes no key. Hit-tests, the keys and every preview then agree with the Document they were worked out from, so a click in the window selects the Anchor or segment under the pointer. The press's preview is drawn on the Document's canvas only. The Direct Selection overlay draws the committed Anchors, at the same places, so a chosen Anchor shows where it is. The Attributes panel shows the pressed direction on the subpaths the press names, and the committed one again once a rejection comes (#276).

**The answer numbers the keys.** When the press's Transaction arrives, or the Document sent on reconnect, each key on a subpath the press named is renumbered if that message turned the subpath the other way. A rejection turns nothing, so it changes no key. A key clicked in the window is renumbered with the rest, so it still names the point it named. Another Actor's edit to a path still clears its keys (ADR-0109). Its Transaction is a different message, so it never renumbers a key. The Document sent on reconnect carries no such message, so the browser compares each path the press named with the Document from before: a path whose `d` is the press's preview was reversed and its keys are renumbered, one whose `d` is unchanged keeps its keys, and any other `d` was reshaped by another Actor, so its keys are cleared as ADR-0109 clears them, even when the reshape flipped the winding (#276).

**An edit waits for the answer.** While a press is in flight, a Direct Selection drag's release, Delete (Edit > Clear), Object > Path > Remove Anchor Points, Join and Average, the Anchors bar's Convert buttons, another Reverse Path Direction press, a click of the Add or Delete Anchor Point tool or of the Pen's Auto Add/Delete, a click or drag of the Anchor Point tool, a Curvature drag or double-click on a selected path's Anchor (#276), the Pen continuing or connecting a path at an Endpoint, and a Pencil redraw of a selected path (#278) are held. Each keeps the Anchors, segments, Selection and tool chosen when the person made it, so a click after it does not change what it acts on. Until it runs, its keys are renumbered by the answer and cleared by another Actor's edit to their path, as the Direct Selection's are. Once the press is answered, rejected or settled by a reconnect, the held edits run in order on the Document as it then is, as if each had come just after the press. A held drag whose Handle or segment is cleared that way is dropped. A drag still being made when the answer comes renumbers what it holds, the Anchors, the Handle or the segment, from then on. On a subpath the answer turned, a Handle held is its Anchor's other Handle, and a point on a segment is the same distance from the segment's other end, so an added Anchor or a bend lands where the person clicked. An edit worked out from the Anchor alone, such as the Anchor Point tool's drag out of an Anchor, is worked out again on the Document then, as if it came just after the press. The Pen holds the Endpoints it continues and connects to as keys, and its path is put in place at them, so on a subpath the answer turned it runs the way the press left it; an answer that comes while the Pen is still drawing renumbers its Endpoints the same way. The Pencil holds its Ink, and its redraw is worked out again from it, so it replaces the stretch drawn over. It redraws the path the Ink was drawn over, whatever the Selection is then, and holds the Ink in that path's own coordinates, so the person's Selection tool move sent in the window carries the Ink with the path (#284). It also holds a key on the path it redraws, so another Actor's edit to that path drops the redraw, as it drops the Pen's and every other edit held by key (#281). Any Anchor's key on the path serves: the redraw reads only whether it is still there. A held edit sends nothing until it runs, so its preview stays on screen until then.

**Another Actor's edit ends a Pen continuation** (#282). The Pen keeps a continued path in the browser until it finishes (ADR-0032), seeded with the Anchors its subpath had when the person clicked its Endpoint. The finish sets that subpath to those Anchors plus the new ones. So if another Actor's edit to the path came in meanwhile, the finish wrote the old Anchors back over it. In Illustrator each Pen click is already in the document, so an edit made between clicks applies on top of what was drawn, and the next click acts on the path as it then is. Kalamo cannot do the same: a Transaction does not say how it renumbered the Anchors, which is why ADR-0109 clears the keys on a path someone else changed. So the rule for a held Pen edit applies to one still being drawn. When another Actor's Transaction updates or deletes the path the Pen continues, the continuation ends at once. The Pen's path and its preview go, so the canvas shows the path as the other Actor left it. Nothing is sent, and a notice tells the person that what the Pen drew was not applied. The next click starts a new path, or continues the changed one from an Endpoint. The Document sent on reconnect does not say who changed the path, so the continuation ends there when the path is in any way unlike the one before and unlike what a press in flight makes of it. The person's own Transactions, those the browser tracks as its own, leave the continuation alone. A continuation of a path no one else touches finishes as before, including on the Endpoints a press's answer renumbers. In `apps/web/src/receive.ts`, `viewAfter` ends it.

**Another Actor's edit drops a held Pen connection** (#290). A Pen press on another path's Endpoint, while the Pen is drawing, connects to it on release, and from the press to the release the Pen names that Endpoint by node, subpath and end. The button can stay down as long as the person drags a Handle out of the Endpoint. When another Actor's Transaction updates or deletes the path the press connects to in that time, the connection is dropped at once, as Esc during the press drops it: the Anchor added on the Endpoint goes, the Pen goes on drawing its path as it was before the press, and its preview shows that. The press is no longer a connection, so a drag after the drop moves no Handle and the release finishes and sends nothing. A notice says that someone else changed the path the Pen was connecting to and the connection was not made; it is joined with the other notices of the same message (#291). The next press connects to the path as it now is. In Illustrator the connection is made at the click, on the path as it is then. Kalamo cannot carry the press onto the changed path, for the reason ADR-0109 gives for every key, so it drops only the connection and keeps the person's drawing, which no one else touched. If the same edit also reaches the path the Pen continues, including a press that connects to another subpath of that path, the rule above applies and the whole continuation ends. The Document sent on reconnect, the person's own Transactions, and edits to other paths are read as for a continuation. In `apps/web/src/receive.ts`, `viewAfter` drops it; in `apps/web/src/tools.ts`, a connect press without its Endpoint neither drags nor finishes.

**Another Actor's edit that drops drawn work tells the person** (#291). A held Pen finish (continue, connect or close) whose Endpoint keys another Actor's edit cleared, and a held Pencil redraw whose key it cleared, send nothing and their previews go, as before. A notice now says so: for the Pen, that someone else changed a path the Pen was continuing or connecting to and what it drew was not applied; for the Pencil, the same notice its own drop gives (#284). Drawn work is announced because it cannot be seen again once its preview goes, and it costs the person a redraw; unannounced, the person may take the vanished preview for an applied edit or a glitch and move on without it. A dropped Direct Selection, Anchor Point or Curvature drag, and the other held edits, stay silent: their target is still on screen, and one drag repeats them. A notice that drops drawn work is never replaced by another notice from the same message: the drop notices of the held edits a message runs, the Pen notice of a continuation it ends, the "Skipped N object(s)" notice of an Undo or Redo that skipped Nodes, and the reason a rejected press gives are joined into one notice, drawn work's first. In `apps/web/src/store.ts`, `runHeld` joins the notices the held edits set to the notice of the message that answered, so a held edit's notice no longer replaces that message's; in `apps/web/src/receive.ts`, `viewAfter` joins its own.

**A held edit's preview is its own** (#283). When an edit is held, the preview its gesture drew goes with it, so the next gesture draws its own preview beside it and several held edits all stay on screen. When a held edit runs, its preview gives way to the preview of what it sends, which stays until that command is answered. When it is dropped, its preview goes. Either way no other preview changes: not another held edit's, not one of the person's edits sent and not yet answered, and not the preview of a drag the person is making then, with any tool, which goes on and on release sends what the person dragged. In `apps/web/src/store.ts`, `afterReverse` takes the gesture's unsent preview into the held edit when the caller says it is the edit's (`previewed`), and `runHeld` runs each held edit on that preview alone, keeps what it sent in `ran` until answered, and puts the other previews back.

**The type of `send` enforces the wait** (#277). In `apps/web/src/store.ts`, `send` takes a command that names Anchors, Handles or segments by index only with a second argument, `Waited`: a `path_edit`, a `path_join`, or a `path_op` given `anchors`. Every other command, `NodeCommand`, needs none. `afterReverse` is the one place that holds an edit, and it hands each edit the `Waited` to send with. An edit that does not wait says so with `unheld(why)` at its call site, so `grep unheld` lists every edit by index that is not held and the reason. A new edit by index that does neither fails `tsc`, and `store.test.ts` fails `tsc` if `send` stops refusing one. A `path_reverse` names subpaths, which a reverse does not renumber, so it is a `NodeCommand`. A second press waits because the store tracks one press in flight, and `AttributesPanel` sends it through `afterReverse`.

## Considered Options

- **Renumber at the press and hit-test the reversed preview (ADR-0109 as built).** Accepted presses would be right if the browser hit-tested and edited the preview. Rejected: a rejected press still has to renumber every edit sent in the window. Delete's `set_d` cannot be renumbered, since its new subpaths do not map one to one onto the old ones.
- **Send the edit at once, with a reverse before and after its ops.** Rejected for the same reason: it holds only for ops that keep every subpath, and Delete and Remove Anchor Points do not.
- **Refuse Direct Selection edits while a press is in flight.** Rejected: the person sees a reversed path and a chosen Anchor and gets nothing, and the window can be long on a slow socket.
- **Check in `send` at run time that no edit by index goes out while a press is in flight** (#277). Rejected: it fails only when a test drives that edit inside the window, which is the case a new edit's tests leave out. A type fails every build.
- **On a reconnect, take a subpath that runs the other way for the press's reverse (as built in #274).** Rejected: another Actor's reshape can flip the winding too, and its keys would then be renumbered onto Anchors ADR-0109 drops (#276).
- **Keep the Anchors a Pen continuation drew when another Actor's edit ends it, as a new path still being drawn** (#282). Rejected for the reason #284 gives for the Pencil: the person drew an edit, not new art, and the new path would start at an Endpoint the other Actor may have moved or deleted. Losing the Anchors costs the person a few clicks, and the notice says so.
- **Put a Pen continuation's Anchors onto the changed path, at once or at the finish** (#282). Rejected: the browser cannot tell which Anchor of the changed subpath is the Endpoint clicked, as ADR-0109 says of every key.
- **Hold every input on the canvas, not just edits.** Rejected: a click selects correctly without waiting, and panning or zooming would stall for the window.

## Consequences

- On a slow socket, an edit made in the window lands a round trip late. Its preview shows until then.
- While the socket is down with a press in flight, held edits wait for the Document sent on reconnect. A tab switch drops them, as it drops every preview.
- A Selection tool drag moves whole Nodes, and is the one edit that passes `unheld`, to the drag commit it shares with the held edits.
- A held edit's preview is worked out on the Document from before the press's answer. Behind a second press, an edit still held on a subpath the first answer turned shows its preview on the other Anchors until it runs, a round trip at most.
- A reconnect clears the keys on a pressed path whose `d` another Actor changed in any way, even a change that kept its winding and its Anchors' order. The Document sent on reconnect does not say what changed, so this is the cautious reading of ADR-0109.
- A held Pencil redraw whose Ink no longer starts on the path drawn over, for a reason other than another Actor's edit (#281), does this (#284):
  - **The person changes the Selection.** Nothing changes. The redraw acts on the path drawn over, which was selected when the Ink was drawn, and never on a path selected later.
  - **The person moves the path with the Selection tool.** The move changes only the path's `transform`, and the Ink moves with it, so the stretch drawn over is redrawn and the path stays where it was moved. Illustrator, which finishes the redraw before it takes the move, leaves the same result. An Alt-drag copy leaves the path where it was, so the redraw lands on it and the copies keep the stretch as it was. Illustrator, which redraws first, copies the redrawn path; the copies are new Nodes the held redraw holds no key on, so this is accepted.
  - **The answer to the person's own edit sent before the press reshapes the path** so that the Ink no longer starts on it. The redraw is dropped: nothing is stored, its preview goes, and a notice tells the person that the Pencil edit was not applied. It does not become new art. In Illustrator, Ink that starts on a selected path always edits that path, in input order, so no order of the same input makes it new art. New art would add a path the person drew as an edit, on top of art they may not see moved.
  - **The person's own command that the browser does not track as its own**, such as Hide or Lock in the Layers panel, Delete, a Fill or Stroke change, or Undo, clears the redraw's key as another Actor's edit does, so the redraw is dropped with the Pencil's notice (#291). For Delete this matches Illustrator, where the redraw and then the deletion leave nothing. The other cases drop every held edit the same way, not only the Pencil's, and are a separate change.
- The person's own command that the browser does not track as its own, such as Undo or a Fill change, ends a Pen continuation on its path, as another Actor's edit does (#282), and drops a held Pen finish on it, so their notices name someone else for the person's own command (#291).
- Another Actor's edit to the path a held Pen press connects to drops the connection, never joins it to a renumbered or deleted path (#290). The person loses only the connecting Anchor and presses the Endpoint again; the person's own command the browser does not track as its own drops it too, with a notice that names someone else.
- While the socket is down, `send` drops the person's commands, so the Document sent on reconnect brings no own edit made during the outage. The person's Selection tool move sent before the socket dropped, with its answer lost, may show in that Document or not, and the Ink follows the path's `transform` either way. Whether another Actor's change to the path during the outage drops the redraw is #287's rule for paths the press did not name, not this one.
