# Edits by index wait for the person's own renumbering command

Retitled by #298 from "Direct Selection waits for a Reverse Path Direction press in flight": the window it opens for a press now opens for every command of the person's own that may renumber a path's Anchors.

ADR-0109 renumbered the Direct Selection's Anchors and segments at a Reverse Path Direction press, to where the reverse would put them, and #272 numbered them back on a rejection. Until the answer came, the browser still hit-tested and edited its committed Document, which was not yet reversed. So a key the person clicked in that window was numbered against the old Document, and #272 flipped it with the others on a rejection. A drag, a Delete or a convert in the window worked out its `path_edit` from keys and a Document that disagreed. Its indices were then applied after the reverse if the press was accepted, and without it if the press was rejected. Either way, some outcome edited a point the person did not choose (#274).

## Sources

- Adobe, *Select anchor points to modify paths in Illustrator* (helpx.adobe.com/illustrator/desktop/draw-shapes-and-paths/modify-paths/select-anchor-points-in-paths.html): the Direct Selection tool selects the anchor points and segments under the pointer, and the next edit acts on those.
- Illustrator runs a command to its end before it takes the next input. A click or a drag after a press of Reverse Path Direction in the Attributes panel meets the reversed path, so nothing in Illustrator sees the press half done. Kalamo's window between the press and its answer has no counterpart there.
- Illustrator applies Object > Path's commands (Outline Stroke, Offset Path, Reverse Path Direction, Simplify, Add Anchor Points, Divide Objects Below, Split Into Grid, Clean Up), Object > Shape > Expand Shape (`convert_to_path`), Object > Compound Path's Make and Release, and the Pathfinder panel's buttons to the art as the person's earlier input left it. A drag of an Anchor followed by one of them reshapes or replaces the dragged path, and Undo then undoes the command before the drag (#289).
- Illustrator runs an Add Anchor Point or Delete Anchor Point click, Edit > Clear on chosen Anchors and Object > Path > Remove Anchor Points to its end before it takes the next input too. A press after an Add Anchor click meets the path with the new Anchor; adding an Anchor moves no other one, so pressing an Anchor and dragging it moves that Anchor. A second Delete Anchor click deletes the Anchor clicked (#298).
- ADR-0010: browser commands carry no `rev`, and the Document DO applies one socket's commands in order. Ops such as `move_anchor`, `set_handles`, `set_point_type` and `remove_anchor` name an Anchor by its index, and Delete's `set_d` writes each subpath's direction. Neither kind gives the same result before and after a reverse.

## Decision

**The keys stay numbered as the committed Document runs until the press is answered.** The press sends `path_reverse` and draws its preview, but it changes no key. Hit-tests, the keys and every preview then agree with the Document they were worked out from, so a click in the window selects the Anchor or segment under the pointer. The press's preview is drawn on the Document's canvas only. The Direct Selection overlay draws the committed Anchors, at the same places, so a chosen Anchor shows where it is. The Attributes panel shows the pressed direction on the subpaths the press names, and the committed one again once a rejection comes (#276).

**The answer numbers the keys.** When the press's Transaction arrives, or the Document sent on reconnect, each key on a subpath the press named is renumbered if that message turned the subpath the other way. A rejection turns nothing, so it changes no key. A key clicked in the window is renumbered with the rest, so it still names the point it named. Another Actor's edit to a path still clears its keys (ADR-0109). Its Transaction is a different message, so it never renumbers a key. The Document sent on reconnect carries no such message, so the browser compares the geometry, as ADR-0109 defines it, of each path the press named with the Document from before: a path whose geometry is the press's preview was reversed and its keys are renumbered, one whose geometry is unchanged keeps its keys, and any other geometry was reshaped by another Actor, so its keys are cleared as ADR-0109 clears them, even when the reshape flipped the winding (#276). On a path the press did not name, a held edit's keys are cleared when the path's geometry, as ADR-0109 defines it, is not as it was, and the held edit is dropped (#287). A held edit runs without the person seeing the path again, so on a path someone else redrew it would rework the Pencil's Ink on Anchors the person never saw, or drag whatever Anchor now has the old index. The live Direct Selection keys on such a path stay while in range, as on a reconnect with no press: the person sees the reconnected Document before acting on them. In `apps/web/src/receive.ts`, `viewAfter` has one reading of "changed" on the Document sent on reconnect, `reshaped`: the geometry is neither as it was nor as the press's preview leaves it. The keys, the held edits, a drag still being made and the Pen all read it. A live Pen continuation also reads its path's `transform`: it holds the Anchors it continues where the Document showed them, so a move of the path, which leaves its geometry, ends it on reconnect (#287). A held Pen finish does not: it holds what it draws in its paths' own coordinates, as the next paragraph says, so a move carries it (#301).

**An edit waits for the answer.** While a press is in flight, a Direct Selection drag's release, Delete (Edit > Clear), Object > Path > Remove Anchor Points, Join and Average, the Anchors bar's Convert buttons, another Reverse Path Direction press, a click of the Add or Delete Anchor Point tool or of the Pen's Auto Add/Delete, a click or drag of the Anchor Point tool, a Curvature drag or double-click on a selected path's Anchor (#276), the Pen continuing or connecting a path at an Endpoint, and a Pencil redraw of a selected path (#278) are held. Undo, Redo and Edit > Cut's delete wait too (#288). They name no Anchor by index; they wait so that the Document DO applies them after every edit the person made before them, in input order, as Illustrator does. Sent at once, an Undo would undo the press and leave the held drag to edit the un-reversed path by renumbered indices, and Cut's delete would make the held edit fail as if someone else had deleted the path. Every `path_op` on whole Nodes waits too, for the same reason (#289): the Object > Path items (Outline Stroke, Offset Path, the menu's Reverse Path Direction, Simplify, Add Anchor Points, Divide Objects Below, Split Into Grid and Clean Up), Object > Shape > Expand Shape (`convert_to_path`), Object > Compound Path's Make and Release, and the Pathfinder panel's Shape Mode and Pathfinder buttons. They name no index, but they reshape or replace paths that held edits name by index. Sent at once, the op was applied first and the held edit then ran on the op's result by indices worked out before it: after Add Anchor Points, Simplify, Clean Up's Stray Points or the menu's reverse, an index named another Anchor or a new midpoint; after an op that replaced the path, the edit failed as if someone else had deleted it; and Offset Path's copy was offset from the path before the held drag. A held op keeps the Nodes chosen when the person made it, the Selection at the click or the paths a dialog or bar opened with, and runs on the Document as it then is. It names no key, so no one's edit drops it; a Node another Actor deleted meanwhile is rejected by the server as before. An op whose result becomes the Selection registers that when it is sent. Clean Up counts its notice on the Document it runs on, so the notice matches what the server removes. After OK, a held Simplify, Offset Path or Split Into Grid keeps its preview on screen while it waits and until its answer, so nothing flickers. If the person opens another op's preview meanwhile, the held op's preview gives way to it; the held op still runs and is sent, and its result appears with its answer. The single op-preview slot stays one slot. Cut puts the art on the clipboard at once. The Pen's Undo of its last Anchor sends nothing and runs at once. Each keeps the Anchors, segments, Selection and tool chosen when the person made it, so a click after it does not change what it acts on. Until it runs, its keys are renumbered by the answer and cleared by another Actor's edit to their path, as the Direct Selection's are. Once the press is answered, rejected or settled by a reconnect, the held edits run in order on the Document as it then is, as if each had come just after the press. A held drag whose Handle or segment is cleared that way is dropped. A drag still being made, with Direct Selection, the Anchor Point tool or the Curvature tool, is renumbered only by the answer to the person's own press: the answer renumbers what it holds, the Anchors, the Handle or the segment, by the same rule and in the same step as the held keys and targets, and it goes on from there. Another Actor's Transaction that updates or deletes a path drops what the drag holds on that path, in the same step that clears the keys there, with or without a press in flight (#297). A Transaction does not say how it renumbered the Anchors, so the drag is never carried onto the changed path. When that is all the drag holds, its preview goes in the same step, so the canvas shows the path as the other Actor left it, and the rest of the gesture is inert: a move draws nothing, and the release sends and holds nothing. A Direct Selection drag of Anchors on several paths lets go only of those on the path reached, as the keys are cleared per path, and goes on with the rest. The answer to the person's press brings back nothing dropped this way. Only the drag's own commands keep what it holds on a path that a Transaction reshapes: the answer to the person's previous drag, sent before this drag began, so the browser still counts a sent drag as its own once the next drag's preview replaces it on screen, and the answer to the press, which renumbers it. Any other of the person's own commands that changes the path's geometry (ADR-0109) drops what the drag holds there in the same way, silently (#288). That includes a held edit that ran, such as a Pencil redraw or a Pen finish, Undo, Redo, a `path_op` and a `path_edit` the browser did not draw: the drag's targets were worked out on the path as the press found it, not for that command, which may have renumbered them. Since #298 such a command opens the window too, and the answer to one whose renumbering the browser can work out, such as an Add Anchor click, renumbers what the drag holds instead, as "The answer numbers what waited" below says. The person's own Appearance, `transform`, visibility, lock or stacking change, and edits to other paths, leave the drag alone. The Document sent on reconnect is read as for a Pen continuation (#282): a path whose geometry is unlike the one before the socket dropped, other than exactly what the press in flight makes of it, drops what the drag holds on it; an unchanged path keeps the drag, and the press's reverse renumbers it (#296). A change to the path's Appearance, opacity, name, visibility or lock alone keeps the drag, as the person's own such change does: the drag edits only geometry, so nothing it stores conflicts with it (#287). On a subpath the answer turned, a Handle held is its Anchor's other Handle, and a point on a segment is the same distance from the segment's other end, so an added Anchor or a bend lands where the person clicked. A held edit on one Anchor, Handle or segment keeps it as its target, and its keys are the target's. The answer turns the target by the same rule that renumbers the keys, and drops it when its key goes. The edit then reads only that target. It never compares the subpath's direction again, so it cannot confirm one Anchor and edit another (#280). In `apps/web/src/direct.ts`, `turnTarget` is that rule and `targetKeys` turns a target into keys; in `apps/web/src/receive.ts`, `viewAfter` turns held targets and `grabbed`, the store's record of what a drag still being made holds, and drops from `grabbed` what stands on a path someone else changed or another of the person's own commands reshaped, so no gesture compares directions or reads the Transaction itself, and draws the drag's unsent preview again from what it then holds through `regrab`, which the tool set at the press; in `apps/web/src/canvas.ts`, `sendPreview` commits a held drag, and one that drops it sends nothing. An edit worked out from the Anchor alone, such as the Anchor Point tool's drag out of an Anchor, is worked out again on the Document then, as if it came just after the press. The Pen holds the Endpoints it continues and connects to as keys, and its path is put in place at them, so on a subpath the answer turned it runs the way the press left it; an answer that comes while the Pen is still drawing renumbers its Endpoints the same way, through the same rule for keys (#280). A held Pen finish holds the Anchors it continues and the person's new ones in the own coordinates of the path it continues or connects to, measured through that path's world transform on the Document it was worked out on, and places them through the path's world transform on the Document when it runs, as the Pencil holds its Ink below. A change to only the path's `transform`, by the person's Selection tool move in the window, a move of its Group, which moves the Group's leaves (a Group has no matrix), or a reconnect, carries the finish with the path, so the path is stored extended and moved, as Illustrator, which finishes before it moves, leaves it (#301). A `path_join` of two different paths holds what it draws in the own coordinates of both; when the two moved by different amounts on the Document the Join lands on, the person's Anchors cannot meet both Endpoints, so the finish is dropped. That Document has the person's Selection tool moves sent before the Join, answered or not: the press was sent before the move, so its answer usually comes first, and the Document DO still applies the move before the Join. In `apps/web/src/tools.ts`, `landing` reads it from `sentPreviews`. When dropped, nothing is sent, its preview goes, and a notice says that a path the Pen was connecting to moved before the connection was made, without naming who moved it, since the browser cannot tell the person's own move from one a reconnect brings. The Pencil holds its Ink, and its redraw is worked out again from it, so it replaces the stretch drawn over. It redraws the path the Ink was drawn over, whatever the Selection is then, and holds the Ink in that path's own coordinates, so the person's Selection tool move sent in the window carries the Ink with the path (#284). It also holds the keys of the path's Anchors, so another Actor's edit to that path, which clears them all, drops the redraw, as it drops the Pen's and every other edit held by key (#281). The redraw reads only whether any is still there, so the answer to the person's own Delete Anchor click, which clears only the key it removes, leaves it to run (#298). A held edit sends nothing until it runs, so its preview stays on screen until then.

**The person's own renumbering command opens the same window** (#298). A press is one case of a wider rule: until the answer to a command of the person's own that may renumber a path's Anchors arrives, as a Transaction or a rejection, or the Document sent on reconnect settles it, every edit held for a press waits for it in the same way, in input order. A command opens the window when it may add, remove, reorder or rewrite a path's Anchors: a `path_edit` whose ops include `add_anchor`, `remove_anchor`, `set_d`, `open`, `close` or `reverse`, a `path_join`, any `path_op`, Undo and Redo, a `delete`, which takes its paths' Anchors away, and the press. Its senders include the Add and Delete Anchor Point tools and the Pen's Auto Add/Delete, Edit > Clear on chosen Anchors or segments, the Curvature tool's Clear, Object > Path > Remove Anchor Points, Join and Average, a Pen finish, a Pencil redraw, and every Object > Path, Shape, Compound Path and Pathfinder command. A command that keeps the numbering opens nothing: a `path_edit` of `move_anchor`, `set_handles` and `set_point_type` alone, a `transform`, Appearance, visibility, lock, stacking, and every other `NodeCommand`. So two quick Direct Selection drags still go out at once (#297). A renumbering command sent while the window is open is itself an edit that waits, so at most one is unanswered per tab: quick Delete Anchor clicks go out one round trip apart, each hit-tested on the Document as the person saw it and renumbered by the answer before it. Clicks and Direct Selection's marquee still select at once. In `apps/web/src/store.ts`, `record` opens the window as it records the command's id: it asks `opening` in `apps/web/src/receive.ts` how the command renumbers, and keeps the answer in `renumbering`, by command id; `waiting` is what `afterReverse` and `runHeld` check, the press or any entry there.

**The answer numbers what waited** (#298). The browser built the command's ops, so for most of them it knows where each Anchor goes. In `apps/web/src/direct.ts`, `renumberingOf` applies a `path_edit`'s `add_anchor`, `remove_anchor`, `move_anchor`, `set_handles` and `set_point_type` ops to the path's Anchors, each tagged with its subpath and index, and reads where each tag ended up; it also records where an `add_anchor` split a segment. Edit > Clear's and the Curvature tool's Clear's `set_d` are worked out from tagged Anchors too, and `sendAnchorEdits` hands that `Renumbering` to the store with `renumbers`. The answer to such a command renumbers, through `renumberTarget` next to `turnTarget`, the live Direct Selection keys, the held edits' keys and targets, what a drag still being made holds (`grabbed`), and the held edits' unsent previews; that drag's unsent preview is drawn again from what it then holds. Each keeps naming the Anchor, Handle or segment it named. A key on an Anchor the command removed is cleared, and a held edit that stood on it is dropped silently, as a held edit whose keys another Actor cleared is. A segment between two Anchors that are no longer next to each other is cleared; a point on a segment one `add_anchor` split is on the half it lies on, at the same place, so a drag of it goes on, but a selected segment so split names neither half, since the person chose neither. A drag still being made goes on through such an answer, renumbered, where #288 let go of it; its release, once the window is closed, is sent at once. The answer is used only on the numbering it was worked out for: if another Actor's Transaction changed the path's subpaths or Anchor counts meanwhile, the keys there are already cleared, and the answer is read as one the browser cannot number. The answer to a command the browser cannot number, a `delete`, Undo, Redo, a `path_op`, a `path_join`, a Pen finish's or Pencil redraw's `set_d`, or a `path_edit` with `open`, `close` or `reverse`, keeps #288's rule unchanged: keys on a path whose geometry it changed are cleared, held edits and a drag still being made on that path are dropped, and a key on a path whose geometry it left stays. A held Pencil redraw is worked out again from its Ink on the Document after the answer; it runs if any of its keys survived, and is dropped with its notice if none did, as after a command the browser cannot number that reshapes its path. A rejection renumbers nothing, and the held edits run on their keys as they were. Another Actor's Transaction keeps ADR-0109's rule. The Document sent on reconnect with such a command unanswered cannot say whether it was applied, so it settles the window cautiously: a path whose geometry is unchanged keeps its keys, held edits and drag, and on any other path they are dropped, as #287 reads paths it cannot account for; a press in flight keeps #276's rule for the paths it names. A Pen continuation or connection on a path the answer reshapes is still ended or dropped as #288 says (#293).

**Another Actor's edit ends a Pen continuation** (#282). The Pen keeps a continued path in the browser until it finishes (ADR-0032), seeded with the Anchors its subpath had when the person clicked its Endpoint. The finish sets that subpath to those Anchors plus the new ones. So if another Actor's edit to the path came in meanwhile, the finish wrote the old Anchors back over it. In Illustrator each Pen click is already in the document, so an edit made between clicks applies on top of what was drawn, and the next click acts on the path as it then is. Kalamo cannot do the same: a Transaction does not say how it renumbered the Anchors, which is why ADR-0109 clears the keys on a path someone else changed. So the rule for a held Pen edit applies to one still being drawn. When another Actor's Transaction updates or deletes the path the Pen continues, the continuation ends at once. The Pen's path and its preview go, so the canvas shows the path as the other Actor left it. Nothing is sent, and a notice tells the person that what the Pen drew was not applied. The next click starts a new path, or continues the changed one from an Endpoint. The Document sent on reconnect does not say who changed the path, so the continuation ends there when the path's geometry is unlike the one before and unlike what a press in flight makes of it; a change to its Appearance alone leaves the continuation, as the person's own does, and a move of the path ends it (#287). A continuation the reconnect keeps also keeps its preview, worked out again on the new Document; sent previews still go (#292). The person's own Transactions leave the continuation alone unless they reshape the path, as the Consequences say (#288). A continuation of a path no one else touches finishes as before, including on the Endpoints a press's answer renumbers. In `apps/web/src/receive.ts`, `viewAfter` ends it. An edit that reaches only the path a held press connects to drops that connection and leaves the continuation, as the next paragraph says (#290).

**Another Actor's edit drops a held Pen connection** (#290). A Pen press on another path's Endpoint, while the Pen is drawing, connects to it on release, and from the press to the release the Pen names that Endpoint by node, subpath and end. The button can stay down as long as the person drags a Handle out of the Endpoint. When another Actor's Transaction updates or deletes the path the press connects to in that time, the connection is dropped at once, as Esc during the press drops it: the Anchor added on the Endpoint goes, the Pen goes on drawing its path as it was before the press, and its preview shows that. The press is no longer a connection, so a drag after the drop moves no Handle and the release finishes and sends nothing. A notice says that someone else changed the path the Pen was connecting to and the connection was not made; it is joined with the other notices of the same message (#291). The next press connects to the path as it now is. In Illustrator the connection is made at the click, on the path as it is then. Kalamo cannot carry the press onto the changed path, for the reason ADR-0109 gives for every key, so it drops only the connection and keeps the person's drawing, which no one else touched. If the same edit also reaches the path the Pen continues, including a press that connects to another subpath of that path, the rule above applies and the whole continuation ends. The Document sent on reconnect, the person's own Transactions, and edits to other paths are read as for a continuation. The Pen's press (its kind, the Anchor it edits, the drag origin and the Alt state) is kept in the store beside the Pen's path. In `apps/web/src/receive.ts`, `viewAfter` drops the connection through `disconnected`, which also makes the press inert in the same step, so the Pen tool reads only the press to know whether it still connects (#280).

**Another Actor's edit that drops drawn work tells the person** (#291). A held Pen finish (continue, connect or close) whose Endpoint keys another Actor's edit cleared, and a held Pencil redraw whose key it cleared, send nothing and their previews go, as before. A notice now says so: for the Pen, that someone else changed a path the Pen was continuing or connecting to and what it drew was not applied; for the Pencil, the same notice its own drop gives (#284). Drawn work is announced because it cannot be seen again once its preview goes, and it costs the person a redraw; unannounced, the person may take the vanished preview for an applied edit or a glitch and move on without it. A dropped Direct Selection, Anchor Point or Curvature drag, held or still being made (#297), and the other held edits, stay silent: their target is still on screen, and one drag repeats them. A notice that drops drawn work is never replaced by another notice from the same message: the drop notices of the held edits a message runs, the Pen notice of a continuation it ends, the "Skipped N object(s)" notice of an Undo or Redo that skipped Nodes, and the reason a rejected press gives are joined into one notice, drawn work's first. In `apps/web/src/store.ts`, `runHeld` joins the notices the held edits set to the notice of the message that answered, so a held edit's notice no longer replaces that message's; in `apps/web/src/receive.ts`, `viewAfter` joins its own.

**A held edit's preview is its own** (#283, #285). When an edit is held, the preview its gesture drew goes with it, so the next gesture draws its own preview beside it and several held edits all stay on screen. When a held edit runs, its preview gives way to the preview of what it sends, which stays until that command is answered. When it is dropped, its preview goes. Either way no other preview changes: not another held edit's, not one of the person's edits sent and not yet answered, and not the preview of a drag the person is making then, with any tool, which goes on and on release sends what the person dragged. A held edit that throws as it runs drops only its own preview: the held edits after it still run on the same answer, and the error is thrown once they have. The store keeps three kinds of preview, each changed only by its own edit. The live slots (`edit` and `drag`) hold the unsent preview of the gesture being made, and nothing else. Each held edit keeps its own. `sentPreviews` lists every sent edit's preview, from a live gesture or a held edit alike, in the order sent, each with the command ids whose answers settle it, and one step settles it for an answer, a rejection or a reconnect. `sent` stays a separate record of every command unanswered (#288), since a command with no preview, such as an Add Anchor click, Edit > Clear, a gradient or Undo, is in `sent` and in no preview; an entry of `sentPreviews` that a held edit sent is marked `fromHeld`, as #288's reading of a drag still being made needs. The canvas draws the previews in the order the Document DO applies their edits: sent edits in the order sent, then held edits in the order they will run, then the live gesture's. So a Selection tool Alt-drag of a path, sent while a Direct Selection edit on it is held, draws its copy of the path as it was, as the server stores it. The Document sent on reconnect loses the answers to the commands in flight, so it clears `sentPreviews`; it leaves the live gesture's unsent preview, of a drag it keeps (#297) or of a Pen continuation it keeps (#292), and draws a drag's again only when it turns, renumbers or lets go of what the drag holds. In `apps/web/src/store.ts`, `afterReverse` takes the gesture's unsent preview off the live slots when the caller says it is the edit's own (`previewed`), into the held edit, or to give way to what the edit sends at once; a held edit runs with no swap of the live slots, since it never writes them; and `drawSent` is the one step by which a sent preview reaches `sentPreviews`. In `apps/web/src/canvas.ts`, `sendPreview` sends a preview and hands it to `drawSent`, and `commitDrag` is a live gesture's release through it. In `apps/web/src/receive.ts`, `settleSentPreviews` settles the list.

**The type of `send` enforces the wait** (#277, #289). In `apps/web/src/store.ts`, `send` takes a `path_edit`, a `path_join` or any `path_op`, on whole Nodes or given `anchors`, only with a second argument, `Waited`. `Waited` means the command is sent after the press in flight, for one of two reasons: it names Anchors, Handles or segments by index, or it reshapes or replaces paths that held edits name by index. Every other command, `NodeCommand`, needs none; a `path_op` on whole Nodes is no longer one. `afterReverse` is the one place that holds an edit, and it hands each edit the `Waited` to send with. An edit that does not wait says so with `unheld(why)` at its call site, so `grep unheld` lists every such command that is not held and the reason. A new one that does neither fails `tsc`, so a new Pathfinder button or Object > Path item waits without being told, and `store.test.ts` fails `tsc` if `send` stops refusing one. A `path_reverse` names subpaths, which a reverse does not renumber, so it is a `NodeCommand`. A second press waits because the store tracks one press in flight, and `AttributesPanel` sends it through `afterReverse`. Undo, Redo and Cut's delete wait for input order as the `path_op`s do, but by call-site convention, through `afterReverse`, not by type: they stay `NodeCommand`s (#288).

## Considered Options

- **Renumber at the press and hit-test the reversed preview (ADR-0109 as built).** Accepted presses would be right if the browser hit-tested and edited the preview. Rejected: a rejected press still has to renumber every edit sent in the window. Delete's `set_d` cannot be renumbered, since its new subpaths do not map one to one onto the old ones.
- **Send the edit at once, with a reverse before and after its ops.** Rejected for the same reason: it holds only for ops that keep every subpath, and Delete and Remove Anchor Points do not.
- **Refuse Direct Selection edits while a press is in flight.** Rejected: the person sees a reversed path and a chosen Anchor and gets nothing, and the window can be long on a slow socket.
- **Check in `send` at run time that no edit by index goes out while a press is in flight** (#277). Rejected: it fails only when a test drives that edit inside the window, which is the case a new edit's tests leave out. A type fails every build.
- **On a reconnect, take a subpath that runs the other way for the press's reverse (as built in #274).** Rejected: another Actor's reshape can flip the winding too, and its keys would then be renumbered onto Anchors ADR-0109 drops (#276).
- **Keep the Anchors a Pen continuation drew when another Actor's edit ends it, as a new path still being drawn** (#282). Rejected for the reason #284 gives for the Pencil: the person drew an edit, not new art, and the new path would start at an Endpoint the other Actor may have moved or deleted. Losing the Anchors costs the person a few clicks, and the notice says so.
- **Put a Pen continuation's Anchors onto the changed path, at once or at the finish** (#282). Rejected: the browser cannot tell which Anchor of the changed subpath is the Endpoint clicked, as ADR-0109 says of every key.
- **Keep the drag's indices across another Actor's edit (as built in #296).** Rejected: a Transaction does not say how it renumbered the Anchors, so after another Actor reverses the subpath or adds an Anchor before the one grabbed, the drag's preview and release edit a point neither Actor chose and partly overwrite the other Actor's edit (#297). Dropping costs the person one drag.
- **Hit-test the path as the person's own renumbering command will leave it, and send the next edit at once with indices mapped forward** (#298). Rejected for the reason the press rejects it: if the earlier command is rejected, the forward indices land on the path it left unchanged, and a `set_d` cannot be mapped back.
- **Drop a drag still being made when the answer to the person's own Add or Delete Anchor click reshapes its path (#288 as built).** Rejected for commands the browser can number: Illustrator keeps the drag, and the person loses the work of the drag for a click they made a moment before. It stays for commands the browser cannot number.
- **Refuse edits while the person's own renumbering command is unanswered** (#298). Rejected as for the press: the person sees the path and gets nothing, and on a slow socket every Add Anchor click would lock the canvas for a round trip.
- **Hold every input on the canvas, not just edits.** Rejected: a click selects correctly without waiting, and panning or zooming would stall for the window.

## Consequences

- On a slow socket, an edit made in the window lands a round trip late. Its preview shows until then. Quick renumbering clicks on one path, such as Add or Delete Anchor clicks, go out one round trip apart, in order, and so does Undo after one (#298). The commands themselves still draw no preview (#285).
- A press is hit-tested on the committed Document, never on what the person's unanswered command will make of it (#298). A press within the hit tolerance of an Anchor an unanswered Add Anchor click is adding grabs the segment the Anchor will split, not that Anchor, and one on an Anchor an unanswered Delete removes grabs that Anchor, and its edit is dropped with it.
- An Object > Path, Shape or Compound Path command or a Pathfinder button used after a held edit applies to the path that edit leaves, as in Illustrator: it no longer moves another Anchor of it, tells the person someone else deleted it, or builds Offset Path's copy from the path before the edit (#289). Its own answer comes after the held edit's, and ADR-0109's rule for keys then clears the keys on every path it reshaped or deleted. Clean Up's notice is counted when it runs, not at OK.
- While the socket is down with a press in flight, held edits wait for the Document sent on reconnect. A tab switch drops them, as it drops every preview.
- A Selection tool drag moves whole Nodes, and is the one edit that passes `unheld`, to the drag commit it shares with the held edits.
- A held edit's preview is worked out on the Document from before the press's answer. Behind a second press, an edit still held on a subpath the first answer turned shows its preview on the other Anchors until it runs, a round trip at most.
- A reconnect clears the keys on a pressed path whose geometry another Actor changed in any way, even a change that kept its winding and its Anchors' order. The Document sent on reconnect does not say what changed, so this is the cautious reading of ADR-0109.
- A reconnect with a press in flight drops a held edit on a path the press did not name whose geometry changed in any way, for the same reason (#287). The Document cannot say who changed it, so this includes the person's own command sent before the socket dropped whose answer was lost, if that command changed the geometry without opening the window. A Selection tool move changes only `transform`, so it keeps the held edit (#284), a held Pen finish included, which goes with the path (#301), and an Appearance, visibility or lock change does too. A renumbering command keeps the window open, so #298's rule drops the edit on a changed path anyway. Dropping is the cautious side: it costs the person a redo, never another Actor's work, and dropped drawn work still says so with its notice (#291): the Pen's names someone else, the Pencil's says its path changed.
- A held Pencil redraw whose Ink no longer starts on the path drawn over, for a reason other than another Actor's edit (#281), does this (#284):
  - **The person changes the Selection.** Nothing changes. The redraw acts on the path drawn over, which was selected when the Ink was drawn, and never on a path selected later.
  - **The person moves the path with the Selection tool.** The move changes only the path's `transform`, and the Ink moves with it, so the stretch drawn over is redrawn and the path stays where it was moved. Illustrator, which finishes the redraw before it takes the move, leaves the same result. An Alt-drag copy leaves the path where it was, so the redraw lands on it and the copies keep the stretch as it was. Illustrator, which redraws first, copies the redrawn path; the copies are new Nodes the held redraw holds no key on, so this is accepted.
  - **The answer to the person's own edit sent before the press reshapes the path** so that the Ink no longer starts on it. The redraw is dropped: nothing is stored, its preview goes, and a notice tells the person that the Pencil edit was not applied. It does not become new art. In Illustrator, Ink that starts on a selected path always edits that path, in input order, so no order of the same input makes it new art. New art would add a path the person drew as an edit, on top of art they may not see moved.
  - **The answer to the person's own other command, sent before the press**, follows ADR-0109's rule for keys (#288). A Fill or Stroke change, the fill rule, Hide, Lock, a reorder or a reparent leaves the path's geometry, so the redraw's key and every other held edit's keys stay and the edit runs once the press is answered. Undo, Redo, a `path_op` or a `path_edit` the browser did not draw that reshapes the path clears them, and the edit is dropped as one another Actor's edit drops, with the Pencil's and the Pen's notices (#291), which still name someone else. Delete and Cut wait for the press, so a held edit runs first and is then deleted with its path, which leaves what Illustrator leaves: nothing, and no notice.
- A held Pen finish goes with its path through a change to only the path's `transform`, as a held Pencil redraw does (#301): the person's own Selection tool move in the window, a move of its Group, or a reconnect that brings such a move. It is dropped only when it joins two different paths (`path_join`) that moved relative to each other, for example when the person dragged one of them; Illustrator would join first and move the joined path, but Kalamo has two paths and can no longer place the person's Anchors on both Endpoints. Nothing is sent, and the notice says that a path the Pen was connecting to moved before the connection was made, naming no one. Another Actor's move of the path, or of its Group, which moves its leaves, still clears the finish's keys, so it is dropped with the notice that names someone else (#282).
- The answer to any of the person's own commands but the press that reshapes the path a Pen continues, such as Undo, their own earlier Pen finish, a Direct Selection drag or a held edit that ran, ends the continuation, as another Actor's edit does (#282), because the Pen seeded its Anchors from the committed Document, before that command; its notice names someone else until #293. A held Pen connection names only an Endpoint, so the answer to the edit the keys were worked out for keeps it, as before (#290). Their own paint, visibility or lock change leaves the continuation to finish.
- Another Actor's edit to the path a held Pen press connects to drops the connection, never joins it to a renumbered or deleted path (#290). The person loses only the connecting Anchor and presses the Endpoint again; the person's own command that reshapes that path drops it too, with a notice that names someone else.
- While the socket is down, `send` drops the person's commands, so the Document sent on reconnect brings no own edit made during the outage. The person's Selection tool move sent before the socket dropped, with its answer lost, may show in that Document or not, and the Ink follows the path's `transform` either way. Another Actor's change to the path's geometry during the outage drops the redraw, as it drops every held edit on that path (#287).
