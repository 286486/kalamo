# A nested `<svg>` opens as a Group, clipped to its viewport when its content overflows

An `<svg>` inside an SVG file establishes a new viewport (SVG 1.1 §7.9, SVG 2 §8.2). Its `x`, `y`, `width`, `height`, `viewBox` and `preserveAspectRatio` place and scale its content, and its `overflow`, `hidden` in the user-agent stylesheet, clips the content to that viewport. Until #237, SVG Open and Place dropped it with everything inside, leaving one `UNSUPPORTED_ELEMENT` warning. `pnpm bench place` found this when an Agent pasted a logo file's whole `<svg>` into a poster. Nested `<svg>`s also come from icon sprites and charting-library exports. This ADR amends ADR-0017's import rules. Export does not change.

## Decision

1. **A Group.** A non-root `<svg>` in the SVG namespace is read as a container in the same branch as `<g>`, `<a>` and `<switch>`. It is one `group` Node, never a Layer: an `inkscape:groupmode="layer"` on it or inside it reads as a Group, and directly under the root it goes into the Layer for loose content (ADR-0073). Its name, Node id (`z-<ULID>` kept), `opacity`, blend mode, `display`, `visibility`, container Appearance, inherited style, and the `mask` and `filter` warnings work as on a `<g>`. It counts as one level toward `MAX_DEPTH`. A read nested `<svg>` raises no warning, and warnings from inside it keep their code and message.
2. **The matrix.** Its children's matrix is the parent matrix, then the element's own `transform`, then `translate(x, y)`, then the viewBox fit. The Group's own transform stays identity, and leaves bake the matrix as under a `<g>` (ADR-0007, ADR-0017), so Live Shapes, text and Images stay what they are. Viewport lengths take the reader's units; `x` and `y` default to 0, `width` and `height` to 100%, and a percentage is of the nearest enclosing viewport in its user units: the root's viewBox size (else its `width` and `height`, else 300 × 150), or the enclosing nested `<svg>`'s. That viewport is also what `userSpaceOnUse` gradient percentages inside it measure against. A valid `viewBox` (four finite numbers, width and height above 0) is fitted to the viewport by `preserveAspectRatio`, default `xMidYMid meet`, through core's `aspectPlacement`, the one fit that an Image's frame also uses. An unreadable `viewBox` or `preserveAspectRatio`, or a negative viewBox size, is ignored as SVG ignores it; without a viewBox the content only translates.
3. **`transform` on `<svg>`.** SVG 1.1 has no `transform` on `<svg>`; SVG 2 adds it. Measured on 2026-10-02 with `<svg transform="translate(50,0)" width="50" height="50">` around a 50 × 50 rect: Chrome 153 draws it once, at x 50 to 100. Inkscape 1.2.2 ignores it and draws at x 0 to 50. resvg 2.6.2, the test oracle, applies it twice: `translate(25,0)` draws at x 50 to 100, and its viewport clip, transformed twice as well, hides `translate(50,0)` entirely. Kalamo follows SVG 2 and Chrome and applies it once. Because resvg does not, the render oracle has no row with a `transform` on a nested `<svg>`; its rotated row rotates a `<g>` around it.
4. **Clipping only on overflow.** `overflow` is read from the attribute, `style` and stylesheet rules, and is not inherited. `hidden`, `scroll`, `clip` and the default clip; `visible` and `auto` do not. A clipping viewport becomes a Clipping Path only when the content read into the Group draws more than 1e-3 pt outside the viewport rectangle, measured by core's `visibleBounds`, Strokes included, in document coordinates. That box is mapped back through the parent matrix and the element's own `transform` into the viewport's own space and compared with the viewport rectangle there, the 1e-3 pt shrunk by that matrix's scale. The Clipping Path is a `rect` Live Shape on top of the Group, `clipping: true`, with an empty Appearance, at the viewport's `x`, `y`, `width` and `height` in the parent's user space (ADR-0021, ADR-0053). Under a rotation or skew, the mapped box is larger than the content, so the test can clip content that never draws outside the viewport, but never misses content that does; that extra clip changes nothing drawn and is accepted. Comparing against the transformed viewport's bounding box instead would be larger still, and miss real overflow.
5. **An empty viewport is dropped.** A resolved `width` or `height` of 0 or less, or a `viewBox` 0 wide or high, draws nothing in SVG. The element and its subtree are dropped with one `INVALID_ELEMENT` warning under one key, naming the nested `<svg>`. A `<g>` left empty by that drop stays.
6. **`clip-path` and a viewport clip make two Groups.** A Group holds one Clipping Path (ADR-0021). SVG applies an element's `clip-path` in its own user space, outside its viewport. So when a nested `<svg>` both names a `clip-path` Kalamo holds and needs its viewport clip, the outer Group holds the `clip-path`'s Clipping Path and an inner Group holds the content and the viewport's rect.
7. **Out of scope.** `<symbol>` and `<use>` in general stay silent, apart from ADR-0056's `<use>` inside `<clipPath>`; their viewport follows the same rule, so their issue reuses this fit and clip. The root `<svg>`'s `preserveAspectRatio` and a root viewBox whose aspect differs from its `width` and `height` keep today's scale, `width / viewBox width`. `overflow` on any other element is not read.

Export writes the Group as any Group, a `<g>` with an inline `<clipPath>` when it is a Clipping Mask; Kalamo never writes a nested `<svg>`. So Open → Export → Open gives the same Nodes. For that, the reader no longer merges a `<g>` into ADR-0056's Clip Group when the `<clipPath>` its children name sits inside one of them: that is Kalamo's own Clipping Mask, which reopened as a Group around a plain Group before, whenever a Group's only child was a Clipping Mask. This amends ADR-0056's Clip Group rule.

## Considered Options

- **A new viewport Node type, or keeping the `<svg>` as raw XML.** Every container walk would gain a type, and ADR-0017 keeps no raw XML. A Group with a baked matrix is what pasting the inner file's elements into a `<g transform>` gives.
- **A Layer.** The Document's Layers sit at the top level (ADR-0073), as Place already keeps them for a placed file's layers.
- **Always clipping, as Illustrator does.** Adobe community reports say Illustrator imports a nested `<svg>` as a Clip Group. Always clipping would add a Clipping Path to every embedded logo, and set its bounds to the viewport (ADR-0021), so an Agent placing against the drawn shapes would place against the viewport instead. Kalamo differs from Illustrator only where the clip changes nothing drawn.
- **Never clipping.** The opened Document would draw overflow that every browser hides.
- **An exact clip test under rotation.** It needs a polygon test of the content against the rotated viewport for a case that draws the same either way.
- **Ignoring `transform` on `<svg>`, as Inkscape 1.2 does.** Browsers draw it, and SVG 2 defines it. Following resvg's double application would follow a bug.

## Evidence

The render package's PNG tests open 16 source files with nested `<svg>`s and compare the opened Document's rendering with resvg's rendering of the source, at most `VECTOR_BUDGET` of the pixels differing: the issue's repro, `x` and `y` without a viewBox, a viewBox scale, `none`, `xMinYMid meet`, `xMaxYMax meet` and `xMidYMid slice`, the default size with percentages and `mm`, the default clip, `overflow="visible"`, two levels, a Stroke overflowing only by its width, a rotated parent twice (once overflowing only within the rotated viewport's bounding box), text, and a `userSpaceOnUse` percentage gradient. Each failed before this change, because the content was missing. With the viewport clip disabled, the slice, default-clip, Stroke and rotated rows fail; with the gradient measured against the root's viewport, the gradient row fails.
