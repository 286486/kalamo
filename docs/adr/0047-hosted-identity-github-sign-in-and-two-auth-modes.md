# Hosted identity: two auth modes, GitHub sign-in and D1 sessions

Until now the Worker had one mode. `/mcp` took a fixed `DEV_TOKENS` Bearer token (ADR-0006), every browser route was unauthenticated (ADR-0009), and every browser edit was the Actor `user` (ADR-0010). The M1 hosted launch puts the Worker on the public internet (#117). This ADR records the first slice (#118): who a request is, how a browser signs in, and how the Document Durable Object learns the Actor; and the second (#119): how a remote MCP client authorizes as an Agent Actor of a User. Document ownership with Roles (slice 3) extends it.

## Decision

- **Two auth modes.** `AUTH_MODE` is `dev` or `github`.
  - `dev` is today's behaviour: MCP takes the `DEV_TOKENS` Bearer tokens, and every browser is the local User `local` with the Actor `user`. `.dev.vars`, the Workers test pool, the e2e suite and the bench and round-trip scripts set it. It is safe only on a private network.
  - `github` is the default in `wrangler.jsonc`, and any value other than `dev` means `github`, so a deploy that sets no mode is never open. It answers every request 500 `server misconfigured` while `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET`, `APP_ORIGIN`, the `DB` binding or the `OAUTH_KV` binding is missing. It ignores `DEV_TOKENS`: `/mcp` takes only MCP OAuth tokens.
- **Principal.** A request resolves to at most one `Principal` `{ userId, actor, access }` through one authentication function per mode. `actor` is the id the Delta Log records. `access` is always `write` for a browser. Every browser route takes its Actor from the Principal. A User's Actor is `user_<userId>`.
- **GitHub sign-in.** A GitHub OAuth App, asked for no scopes, so Zibel reads only the public profile.
  - `GET /auth/github?return=<path>` sends the browser to GitHub with a random `state` kept, with the return path, in a 10-minute HttpOnly `__Host-` cookie.
  - `GET /auth/github/callback` refuses a missing or mismatched `state` with 400. It exchanges the code, reads `GET https://api.github.com/user`, upserts the User by GitHub's numeric id (refreshing the login and avatar), creates the User's `kind='user'` Actor row at the first sign-in, starts a session and redirects to the return path. A return path that is not a same-site path is `/`.
  - The GitHub access token lives only in the callback's memory. Nothing stores it.
  - User ids are Zibel's own ULIDs, not `github:<id>`, because the OAuth provider library forbids `:` in a user id.
- **Sessions in D1.** The cookie `__Host-zibel_session` (`HttpOnly; Secure; SameSite=Lax; Path=/`) holds 32 random bytes. D1 keeps only their SHA-256 with the user id and the created and last-seen times. A session unused for 30 days answers 401; its last-seen time moves at most once a day. The cookie's own lifetime is 400 days, the most a browser keeps, so the server alone decides expiry. `POST /auth/signout` deletes the row, so the cookie stops working at once. `GET /api/me` answers `{ userId, login, avatarUrl, mode }`, the local User in dev mode, or 401.
- **Origin check.** In GitHub mode, every request other than `/mcp` that is not a GET or HEAD, and every WebSocket upgrade, must carry `Origin` equal to `APP_ORIGIN`, or it gets 403 `PERMISSION_DENIED`. This stops other sites from acting with a person's cookie (CSRF, cross-site WebSocket hijacking). SameSite=Lax is the second line of defence. `/mcp` is exempt: it authenticates by a Bearer header, which no page can make a browser send.
- **The Worker sets the Actor on the WebSocket.** The Worker replaces any client-sent `x-zibel-actor` with the Principal's Actor on the upgrade. The Document Durable Object refuses an upgrade without it, keeps it in the socket's serialized attachment, which survives hibernation, and records every command, undo and redo from that socket under it. The Durable Object stays trust-free: only the Worker can reach it (REQUIREMENTS §7.5). The Role joins the header in slice 3.
- **MCP OAuth 2.1: Zibel is its own authorization server in front of GitHub.** In GitHub mode `@cloudflare/workers-oauth-provider` (pinned) wraps the Worker. It serves the protected resource metadata at `/.well-known/oauth-protected-resource/mcp` (`resource` = `MCP_ORIGIN/mcp`, `authorization_servers` = [`APP_ORIGIN`]), the authorization server metadata, dynamic client registration at `/oauth/register`, Client ID Metadata Documents (with the `global_fetch_strictly_public` flag as their SSRF guard), and `/oauth/token` with PKCE S256, refresh token rotation, revocation and RFC 8707 audience binding. Grants and tokens live in `OAUTH_KV`, tokens and codes only by hash and props encrypted by the token. Access tokens last 1 hour; a grant lasts 30 days from its code exchange. `MCP_ORIGIN` defaults to `APP_ORIGIN`. `/mcp` without a valid token answers 401 with `WWW-Authenticate` naming `resource_metadata`.
  - **Scopes.** `zibel:read`, `zibel:write` and `offline_access`. The consent page, not the client, picks them: `zibel:read`, `zibel:write` unless the person ticks read-only, and `offline_access`, since every grant gets a refresh token. `access` in the props is `write` or `read` by that choice; a token refreshed with narrower scopes is `read` whatever its props say.
  - **`GET /authorize`** parses the request through the library first. A signed-out person goes through GitHub sign-in with `/authorize?…` as the return path and comes back. A signed-in one sees a server-rendered consent page: the client's name (escaped, since registration lets anyone choose it), its redirect URI's host, a warning when that host is loopback, whether the client is a verified CIMD domain or self-registered, the signed-in login, a read-only checkbox, Approve and Deny. The library's `beginConsent` binds the form's single-use handle to the browser with a `__Host-` cookie, which is the CSRF token, and sends `frame-ancestors 'none'`. The POST also passes the Origin check.
  - **Approve** makes or reuses the Agent Actor and completes the authorization with props `{ userId, actor, access }` and the Actor in the grant's metadata. An Agent Actor is one `actors` row per User, client id and redirect URI (`kind='agent'`, `redirect_uri` added by migration 0003), whose `id` is the Actor id itself, `agent_<ULID>`, and whose name is "<client name> (<login>)". Re-authorizing the same client id and redirect URI keeps the row and updates its name and access; the library replaces the old grant. Approving a DCR client also retires, with `revoked_at`, the User's other Agent Actors of that client id: the library replaces all of a DCR client's grants for the User whatever the redirect URI, and Claude Code reconnects on a new loopback port, so those Actors have no grant left and would otherwise stay listed as connected. A CIMD client's grants are replaced only on the same redirect URI, so nothing is retired. **Deny**, and any request whose client and exact redirect URI are known but that is otherwise invalid, end with the standard OAuth error redirect (`error`, `state`, `iss`). An unknown client, a mismatched redirect URI, or a used or unbound handle is a local 400 page, never a redirect.
  - **`/mcp`** takes its Principal from the token's props, after one D1 read that the Actor is not revoked, since KV may lag a revocation by up to a minute. The transport stays stateless (ADR-0006).
  - **Connected Agents.** `GET /api/agents` lists the signed-in User's unrevoked Agents (`actorId`, `name`, `access`, `createdAt`). `DELETE /api/agents/:actorId` sets `revoked_at` and revokes every grant whose metadata names the Actor. The row stays, so history keeps the Agent's name. Authorizing the client again makes a new Actor. Listing also retires every Agent with no live grant, one that expired or that the client revoked at the token endpoint (RFC 7009), since the library tells Zibel of neither; an Agent approved in the last 5 minutes is spared, as KV `list` may not show its grant yet. Its `revoked_at` is then the time Zibel found the grant gone, not when it ended. The browser's account menu (the login at the menu bar's right end) opens Connected Agents with Revoke.
- **Browser.** When `/api/me` answers 401, the Document list offers "Sign in with GitHub" and every other page sends the person there with a return path. A signed-in person sees their login, avatar and Sign out at the menu bar's right end. Dev mode shows nothing new.

## Considered Options

- **Sessions in KV.** Cheaper reads, but KV is eventually consistent for up to a minute, so a signed-out cookie would keep working elsewhere. D1 makes sign-out immediate, and slice 3 resolves the session, the User and the Role in one query.
- **A signed cookie with no server state.** No lookup per request, but sign-out could not end it before it expires.
- **Dev mode as the default.** Friendlier locally, but a deploy that forgot the setting would serve a public Worker with no auth.
- **The Actor as a Durable Object RPC argument on the upgrade.** A WebSocket upgrade must go through `fetch`, which carries only a request, so the Actor rides in a header the Worker owns.
- **Sliding the cookie's `Max-Age` with the session.** Each slide would need a `Set-Cookie` on whatever response is in flight. A long-lived cookie with the expiry kept in D1 has one place to look.

- **Proxying GitHub tokens to MCP clients.** GitHub cannot issue tokens whose audience is Zibel's MCP resource, every client would share one OAuth App's identity, and no client would become its own Actor. Zibel issuing its own tokens after a GitHub sign-in avoids all three, and the per-client consent page closes the confused-deputy hole that a proxy in front of one upstream OAuth App opens.
- **No consent page, approving any client of a signed-in person.** Dynamic registration lets any site register a client and send a signed-in person to `/authorize`; without consent it would get a token silently.
- **Hand-rolled OAuth endpoints.** The MCP authorization spec keeps moving (CIMD, RFC 9207, resource indicators); the maintained library tracks it.

## Consequences

- In GitHub mode, a signed-in User and every Agent still reach every Document until slice 3 adds ownership and Roles, and a read-only Agent can still write: slice 3 enforces `access`. Do not treat a GitHub-mode deploy as private until then.
- `doc_changes` and the browser show Actor ids such as `user_01J…`; resolving them to names is a follow-up. The `actors` rows exist for it.
- `pnpm deploy` reads its secrets from `apps/edge/.deploy.vars`, not `.dev.vars`, whose `AUTH_MODE="dev"` must never reach a deployed Worker.
- ADR-0009's and ADR-0010's "until OAuth" consequences end here for the browser, and ADR-0006's `DEV_TOKENS` stay only in dev mode.
- A self-hosted GitHub-mode deploy needs a KV namespace. `examples/claude-code.mcp.json` stays a dev-mode example; a hosted client adds the URL alone.
